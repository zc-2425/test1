## 五、接口清单

### 5.1 通用约定

| 项 | 约定 |
|---|---|
| 基址 | `/api`；版本走 header `X-Api-Version` 而非路径 |
| 分页 | 统一 `?page=1&size=10&keyword=&status=`，`page` 从 1 起；响应 `{ items, total, page, size }` |
| 排序 | `?sort=createdAt&order=desc`（仅列表接口） |
| 时间 | 请求/响应一律 ISO8601 带时区；列表展示用的「2小时前」「从未」由前端相对时间函数渲染，**后端不返回相对时间字符串** |
| 金额 | `costUsd` 用 number（两位小数），展示时前端补 `$` |
| 状态 | 响应中的枚举值即中文原文（`"已发布"`），不传英文 code，避免前端维护两套映射；确需多语言时另加 `statusCode` |
| 错误 | HTTP 语义 + `{ code, message, fieldErrors? }`；`code` 为业务字符串（`WORKFLOW_NOT_FOUND`） |
| 幂等 | 所有创建接口支持 `Idempotency-Key` header（运行/测试类接口必需） |

## 六、前端数据层设计建议

### 6.1 只有一个出口

```
src/api/
├── client.ts          # ApiClient 实现（fetch/axios），唯一出口
├── mock/              # mock adapter，读 src/mock/*.json
├── types.ts           # 实体 TS 类型（与第二节字段表一一对应）
├── auth.ts  explore.ts  workflow.ts  app.ts  knowledge.ts  dataset.ts
├── agent.ts  prompt.ts  llmops.ts  plugin.ts  tool.ts  providers.ts
└── stream.ts          # SSE 封装（fetch + ReadableStream，非 EventSource）
```

规则：

1. **页面/组件只 import `src/api/*.ts` 里的领域函数，禁止直接 `fetch`**；连 `client` 也不在组件里出现。
2. `VITE_USE_MOCK=true` 时，`client.ts` 内部换成 `mockClient`，**上层领域函数的签名与返回值完全不变**；真假切换零改动。
3. mock 数据必须走同一套 TS 类型（`as` 断言 + 运行时 zod 校验可选），避免 mock 字段与真实响应漂移。
4. 领域函数负责 3 件事：拼 URL、收窄类型、把后端原始字段映射成页面模型（如 `sizeText`）；不做业务判断。

`client.ts` TS 草稿：

```ts
export interface RequestOptions {
  signal?: AbortSignal
  headers?: Record<string, string>
  timeoutMs?: number
  skipAuth?: boolean
}

export interface PageQuery {
  page?: number
  size?: number
  keyword?: string
  status?: string
  sort?: string
  order?: 'asc' | 'desc'
  [key: string]: unknown
}

export interface PageResult<T> {
  items: T[]
  total: number
  page: number
  size: number
}

export interface ApiResponse<T> {
  code: number
  message: string
  data: T
  traceId?: string
}

export interface SseEventMap {
  start: { runId: string }
  'node-start': { nodeId: string; nodeType: string; name: string }
  'node-end': { nodeId: string; status: 'success' | 'error'; output?: unknown; durationMs: number; error?: string }
  delta: { content: string }
  result: { output: unknown; tokens?: { input: number; output: number }; costUsd?: number }
  error: { code: string; message: string }
  end: { status: '已完成' | '失败' }
}
export type SseEvent = {
  [K in keyof SseEventMap]: { type: K; data: SseEventMap[K] }
}[keyof SseEventMap]

export interface StreamHandlers {
  onOpen?(): void
  onEvent(evt: SseEvent): void
  onError?(err: unknown): void
  onClose?(): void
}

export interface ApiClient {
  get<T>(url: string, params?: PageQuery, opts?: RequestOptions): Promise<T>
  post<T>(url: string, body?: unknown, opts?: RequestOptions): Promise<T>
  put<T>(url: string, body?: unknown, opts?: RequestOptions): Promise<T>
  patch<T>(url: string, body?: unknown, opts?: RequestOptions): Promise<T>
  delete<T>(url: string, opts?: RequestOptions): Promise<T>
  upload<T>(url: string, file: File | Blob, fields?: Record<string, string>, opts?: RequestOptions): Promise<T>
  /** SSE：POST + fetch ReadableStream，支持 AbortSignal 取消 */
  stream(url: string, body: unknown, handlers: StreamHandlers, opts?: RequestOptions): Promise<void>
  download(url: string, params?: PageQuery, opts?: RequestOptions): Promise<Blob>
}
```

### 6.2 三个「真调用可插拔」接入点

| 接入点 | 接口 | 传输 | 前端契约 | 切真后端时只改 |
|---|---|---|---|---|
| LLM 对话流 | `POST /api/chat/stream` | SSE（`text/event-stream`） | `stream()` + `delta` 增量追加到 `Message.content`；`end` 时落库消息 | `src/api/stream.ts` 的 `mockStream` 换真 URL |
| 工作流运行 | `POST /api/workflows/:id/run` | 二选一：①`202 + runId` + `GET /runs/:runId` 轮询（1s，最多 120 次）；②直接 SSE | 统一走 `useRun` composable，内部用 strategy 切换 | `src/api/workflow.ts` 的 `runStrategy` 常量 |
| 模型连通性测试 | `POST /api/providers/:id/test` | 普通 JSON | 按钮 loading 60s 超时；失败展示 `error`，成功 toast「延迟 412ms」 | `src/api/providers.ts` 的 `testConnection` |

补充两个同构接入点（原型已画按钮但无反馈，建议一并做）：`POST /api/prompts/:id/run`（提示词测试运行，SSE 可复用 chat 通道）、`POST /api/tools/:id/run`（运行工具，同步 JSON 即可）。

### 6.3 SSE 事件格式建议

服务端（`Content-Type: text/event-stream`，`Cache-Control: no-cache`，`X-Accel-Buffering: no`）：

```
retry: 3000

: ping

event: message
data: {"type":"start","data":{"runId":"run-20240115-001"}}

event: message
data: {"type":"node-start","data":{"nodeId":"n-retrieval","nodeType":"知识检索","name":"知识检索"}}

event: message
data: {"type":"delta","data":{"content":"您的订单"}}

event: message
data: {"type":"delta","data":{"content":" A20240115 "}}

event: message
data: {"type":"node-end","data":{"nodeId":"n-retrieval","status":"success","durationMs":412}}

event: message
data: {"type":"result","data":{"output":"您的订单 A20240115 已于 1 月 15 日 10:20 从上海仓发出。","tokens":{"input":42,"output":46},"costUsd":0.12}}

event: message
data: {"type":"end","data":{"status":"已完成"}}
```

约定：

1. **统一信封** `{"type": "...", "data": {...}}`，`type` 是判别式，`data` 是载荷；一个 `data:` 一行，禁止跨行 JSON（跨行会被 SSE 拆成多条）。
2. `delta` 只传增量文本，前端 `content += data.content`；`result` 才给终态全文，前端以 `result` 覆盖（防丢包累积错位）。
3. 错误用 `error` 事件 + `end{status:"失败"}` 收尾，**HTTP 状态保持 200**（流已开始后无法改状态码）；流未开始前的鉴权/校验失败才用 4xx。
4. 心跳：每 15s 发一行注释 `: ping`，防 Nginx 60s 断连。
5. 断线重连：客户端带 `Last-Event-ID`，服务端用 `id:` 字段回放未消费事件；`delta` 事件不回放（直接重发 `result`）。
6. 取消：前端 `AbortController.abort()`；服务端需在 `end` 前收到断连时释放上游 LLM 调用并按已产出的 token 结算成本。
7. 不要用原生 `EventSource`（只支持 GET、不能带 header/body）；用 `fetch` + `ReadableStream` + 手写 `\n\n` 分帧。

### 6.4 Pinia store 划分

| store | 管哪些实体 | 与其他 store 的关系 |
|---|---|---|
| `useAuthStore` | `User`、`Team`（含 LLMOps 设置、安全设置） | 全局最上游；`me` 拉 `User+Team`，供 `useLlmopsStore` 读 `monthlyBudgetUsd` |
| `useUiStore` | 侧栏折叠、Tab 选中、`?alerts=1`/`?settings=1` 弹窗态、toast 队列、`notificationUnreadCount` | 与实体无关，UI 状态唯一归属 |
| `useExploreStore` | 模板卡、统计卡、收藏集合、模板配置 schema | 依赖 `useAuthStore` 判收藏归属 |
| `useWorkflowStore` | `Workflow`、`WorkflowNode`、`WorkflowEdge`、`WorkflowRun`、画布选中/缩放/撤销栈 | 画布图是**单一 store + 深拷贝快照**，禁止节点级 store |
| `useAgentStore` | `Agent`、运行历史、工具挂载关系 | 读 `useToolStore.tools` 做「工具配置」多选 |
| `usePromptStore` | `Prompt`、`PromptVersion`、变量列表、测试运行输入输出 | 读 `useProviderStore.models` 做模型下拉 |
| `useKnowledgeStore` | `KnowledgeBase`、`KbDocument`、索引进度 | 画布「知识检索」节点读 `knowledgeBases` |
| `useDatasetStore` | `Dataset`、`DatasetDocument`、解析进度 | **与 `useKnowledgeStore` 完全隔离**（两个实体） |
| `useToolStore` | `Tool`、运行结果、使用统计 | 被 `useAgentStore`、画布节点引用 |
| `usePluginStore` | `Plugin`、安装状态 | 安装后需 `useToolStore.refetch()` |
| `useProviderStore` | `ModelProvider`、`Model`、`ApiKey` | 模型下拉的唯一来源，被 workflow/prompt/agent/llmops 复用 |
| `useLlmopsStore` | `Alert`、`AbTest`、成本/监控指标、`Trace` | 读 `useProviderStore.models` 做模型维度聚合；告警三页同源 |
| `useChatStore` | `Conversation`、`Message`、流式缓冲 | 与 `useAgentStore` 解耦：Agent 只是 `ownerType` 的一种 |

划分原则：**一个实体域一个 store，跨域只读引用不写入**；`useProviderStore.models` 与 `useToolStore.tools` 是「公共字典」，其他 store 只读。

### 6.5 缓存策略（TanStack Query 式）

即使不上 TanStack Query，也建议自建 `useQuery` 薄封装，保持同一套语义：

| 数据类别 | 策略 | `staleTime` | 失效方式 |
|---|---|---|---|
| 列表类（workflows/apps/knowledge-bases/datasets/agents/prompts/tools/plugins/providers） | 缓存 + 后台刷新 | 30s | 创建/删除/更新成功后 `invalidateQueries(域)` |
| 统计卡/概览（`/explore/stats`、`/llmops/overview`） | 缓存 | 60s | 页面 focus 时 `refetch` |
| 监控/进度类（`/llmops/models`、`/knowledge-bases/:id/index-status`、`/datasets/:id/status`、`/workflows/runs/:runId`） | 定时轮询 + 可见性暂停 | 0 | `refetchInterval` 3–5s，离开页面即停；`document.hidden` 时暂停 |
| 详情类（`/providers/:id`、`/agents/:id`、`/tools/:id`） | 缓存 | 60s | PUT 成功后直接写回缓存（setQueryData） |
| 字典类（`/models`、`/tools`、`/knowledge-bases` 下拉） | 长缓存 | 5min | 显式手动刷新 |
| 设置类（`/llmops/settings`、`/llmops/security/settings`） | 缓存 + 乐观更新 | 5min | 保存失败回滚 |
| 访问日志/审计（`/llmops/security/audit-logs`） | 不缓存（敏感） | 0 | 每次进入重取 |

**必须本地状态（不进缓存）**：画布图编辑态（节点拖拽/连线/撤销栈，仅在 `保存` 时 POST `/graph`）、表单草稿与校验态、弹窗开合、Tab 选中、搜索输入的防抖值、SSE 流缓冲（`content` 增量）、LLMOps 设置弹窗内的未保存开关、模板配置页 7 个 schema 表单的值。

## 七、三条最容易埋雷的数据模型点（实现前必须拉齐）

1. **`KnowledgeBase` 与 `Dataset` 是两套独立实体，同名不同义。** 截图里「产品文档知识库」是 156 文档 / 50 MB / 向量化状态，而「产品知识库」是 156 记录 / 2.3 GB / 解析状态；字段集只共享 `name/description/progress` 三个。合并表或共用 store 的结果是：改知识库分块大小会污染数据集记录数，两个列表页互相串数据。
2. **同一状态词跨实体不同义，且同一实体列表态与详情态不一致。** `错误` 在 Agent（运行失败）/ Provider（密钥失效）/ Model（指标超阈值）上是三件事；Azure OpenAI 列表显示「错误」而详情写「未激活」，Hugging Face 列表「未连接」而详情「活跃」；`Prompt.status` 里「已发布」与「完成」被混用。若用一个全局 `StatusTag` 枚举字典，必然出现「点开 Azure 卡片就变状态」的诡异 bug——必须按实体建枚举、以后端单一字段为准。
3. **工具/提示词的「参数」有两套形态，Agent 的运行次数是假数据。** `Tool` 列表「输入参数」是自然语言（`长文本文档`），创建页却是逗号分隔 schema（`text, targetLang`）；若不拆成 `inputParams` + `inputSchema`，Agent 工具配置卡片渲染出来会是「长文本文档」这种不可执行的字符串。同时 7 个 Agent 详情页的「运行次数」全部写死 156、`App.usageCount`/`Workflow.nodeCount`/`successRate` 因表头错位无真实值——直接把这些 mock 值当基线做统计，会得到「所有 Agent 运行量完全相等」的荒谬结论。
